## Design decisions and why

**Separate bronze/silver/gold schemas** (`workspace.bronze`, `workspace.silver`, `workspace.gold`), not one flat schema with prefixed table names. The plan's "established config" section only listed `workspace.default` as provisioned (for the volume), which created a real ambiguity about where transform tables should live. Asked the user; they picked the standard medallion convention. These schemas are created via `CREATE SCHEMA IF NOT EXISTS` as part of the build, not manually provisioned.

**SQL warehouse resolved dynamically**, never hardcoded. `databricks/warehouse.py` calls `WorkspaceClient.warehouses.list()` and uses whatever it finds (Free Edition provisions one "Serverless Starter Warehouse" per workspace). Avoids a brittle hardcoded warehouse ID.

**The Lakeflow job is a real Databricks Job**, not just more Python run from GitHub Actions. This was a genuine fork in the road: Phase 1's bronze-table proof used the SQL connector driven remotely from GitHub Actions (works fine, technically), but the architecture calls for the transform to run *inside* Databricks via the Jobs API (`git_source` pulls the `.py` files straight from this GitHub repo at run time, executed as `spark_python_task`s on serverless compute). This was de-risked with a standalone probe *before* building the real transform logic — created a trivial job, ran it, confirmed `git_source` + serverless compute actually works on Free Edition, then deleted the probe. That probe surfaced the requirement that serverless tasks need an explicit `environments` block (`environment_version: "3"`) — omitting it fails immediately with a clear error.

**Job definition is idempotent (create-or-update by name).** `trigger_and_poll_job.py` reads `databricks/lakeflow_job_config.yml` and does `jobs.list(name=...)` → `jobs.reset()` if found, `jobs.create()` if not — every single pipeline run. This means the job definition can never drift from what's in git; there's no separate manual "set up the job once" step to forget. Verified by running the pipeline twice in a row and confirming the second run logged "Updated existing job_id=..." with the *same* ID, not a new one.

**Bronze is overwritten each run; silver accumulates via MERGE upsert.** Bronze = whatever's currently in the raw volume (untouched snapshot). Silver tables have natural keys (e.g. `(symbol, date)`, `(repo, snapshot_date)`) and use `MERGE ... WHEN MATCHED UPDATE ... WHEN NOT MATCHED INSERT` so reruns on the same day update in place instead of duplicating, and history genuinely accumulates run over run. Gold tables are fully recomputed (`CREATE OR REPLACE TABLE ... AS SELECT`) every run since they're cheap derivations of the already-accumulated silver history.

**Weekly → daily cadence switch (2026-07-22).** User asked for a feasibility read before committing. Rate-limit review: yfinance/FRED/Wikipedia/arXiv/R2 all have generous headroom at daily volume; GitHub REST API's 5 req/day is trivial even unauthenticated (deliberately skipped `GH_TOKEN` — user's call when offered). The one real unknown is Databricks Free Edition's compute quota, untested at ~30 job-runs/month vs. the ~4/month this was proven against. **Rollback is a single line**: change the cron in `pipeline.yml` back to `"0 6 * * 1"`. Switching also required fixing `dev_momentum`/`research_pace`'s week-over-week columns, which used `LAG(1)` — correct at weekly cadence, silently wrong (day-over-day) at daily cadence. Now `LAG(..., 7)` since one row accumulates per source per day.

**Market data expanded from 1 symbol to 19 total** (`^GSPC` benchmark + 11 SPDR sector ETFs + a 7-symbol AI basket incl. `BOTZ` as the thematic ETF) partway through Phase 3, once it became clear the `sector_rotation` and `ai_vs_market` gold tables were meaningless with only the S&P 500 pulled. This was flagged to the user as a real scope gap against the original plan (Section 4) before implementing, not silently expanded. (Note for a fresh read: this "19" is a historical coincidence, not the same 19 as the AI basket's current size below — the AI basket alone grew to 19 names through three later expansions, on top of the benchmark and 11 sector ETFs, so `ALL_SYMBOLS` is 31 total today.)

**Custom muted/darker color palette**, replacing the dataviz skill's bright default. User wanted darker, more neutral tones that still read clearly in dark mode. Did *not* eyeball this — installed Node specifically to run `validate_palette.js`, iterated through several candidate hex sets against the actual CVD-safety/contrast/lightness-band checks (chroma-floor failures, CVD-separation failures) until both light and dark variants passed every check. Final categorical hues: slate blue `#2d6bab`/`#4a7bc4`, terracotta `#b35a2a`/`#c96b3a`, pine teal `#1f8a6f`/`#2ba17f`, muted ochre `#b8862f`/`#b0832f`, muted mauve `#9c4f6b`/`#b05f7d` (light/dark).

**Every panel needed its own real visualization** (user feedback — dashboard originally had 3 panels with charts and 2 with only stat tiles). Added: an OHLC-style range bar for Market Snapshot (single floating bar now, will read as a poor-man's candlestick chart once multiple days accumulate); a progress meter for Volatility while accumulating toward its 20-day window, switching to a line chart once ready; a 3-bar rate-comparison chart for Macro Backdrop (deliberately *excluding* CPI, which is an index level not a percentage — mixing units on one axis would have been a real dataviz mistake, not just a style choice); a diverging two-bar chart for AI-vs-market spread and a new cs.AI-vs-cs.LG bar for research pace.

**Bar charts of a single day's value were the wrong form for Research Pace and Dev Momentum specifically** (separate round of user feedback, after the above). Both metrics are fundamentally about *change over time* — a bar chart of today's number can never show "accelerating" or "slowing down," no matter how the underlying window is defined. Research Pace's "trailing 7d" count was already a rolling window; the fix was plotting that rolling value over time (a line chart, same pattern as Public Attention) instead of just showing today's snapshot as a bar. Dev Momentum's raw star count barely moves day to day and is dominated by each repo's overall size, so it switches to `weekly_star_growth` (a diverging bar, colored by sign) once that's available at 7 days of history — the level was never the interesting number, the growth rate was. Verified both new code paths by temporarily swapping fabricated multi-day JSON into `docs/data/` locally (never committed) before trusting them, since real history won't exist for weeks — same empirical-verification pattern used throughout this project.

**Failure alerting via GitHub Issues, not Slack/Discord/email.** Considered a webhook-based notification but that requires the user to go create one and add it as a new secret — real setup friction for a "nice to have." GitHub Issues needed nothing new: the workflow already has `GITHUB_TOKEN`, just needed `issues: write` added to `permissions`. Opens an issue labeled `pipeline-failure` on `failure()`, comments instead of duplicating if one's already open (checked via `gh issue list --label pipeline-failure --state open`), and auto-closes it on the next `success()` — a full create/dedupe/recover loop with zero user setup.

**Registered a Databricks Git credential ahead of the repo going private (2026-07-23), rather than just accepting daily transform failures.** The insight that made this worth the setup cost: ingestion and publish never depended on repo visibility (R2/Databricks writes and pushing to your own private repo both work fine) — only `git_source`'s anonymous clone breaks. Fixing just that one piece keeps the *entire* pipeline running daily and accumulating real data throughout the private window, invisible until it goes public again, instead of pausing accumulation for however many weeks it's private. Used the Databricks SDK's `git_credentials.create()` (a fine-grained GitHub PAT, scoped read-only to just this repo) via the same one-off-script-run-once-then-deleted pattern used for everything else that needed real Databricks/R2 credentials this session. Full detail and recovery steps (if the PAT expires before going public again) are in the "Repo is going private" note above.

**Per-chart time-window selector (7D/30D/90D/All), and redefined the "snapshot" charts to be window-aware rather than fixed-to-today (2026-07-24).** User wanted to pick how far back each chart looks, independently per chart, not a single global toggle. Turned out to need surprisingly little backend work: of the 8 gold tables, only `macro_snapshot` was collapsed to latest-only via SQL (`WHERE rn = 1`) — every other table already exported full accumulated history, so the windowing math could live entirely client-side. Removed that one filter (KPI tiles now pick "latest per series" client-side instead, same `latestPerKey` pattern already used elsewhere) and built two small shared primitives: `compoundReturn` (compounds an existing daily % return column over a window — used for Sector Rotation and AI-vs-Market, which already had `daily_return`/`ai_basket_return` columns to compound) and `windowDeltaByGroup` (end-value minus start-value within a window, for level-valued metrics — star counts, macro rates). Redefined Sector Rotation and the Macro rates chart from "today's snapshot" to "change over the selected window," since a fixed daily/current-value snapshot never had a real "time window" concept to select in the first place — the window selector forced that redefinition, not just a UI addition. Each chart keeps independent state via a closure-scoped `days` variable and a `draw()` function that rebuilds just that chart's canvas on selection change (verified interactively — a real headless-browser button click, not just a static screenshot — that this re-render path doesn't hit Chart.js's "canvas already in use" error). Caught a real mobile bug in the process: the `.panel-grid`/`.two-col` mobile media query used a plain `1fr` track instead of `minmax(0, 1fr)` like every other grid rule in the file — harmless until the new `.window-selector`'s `flex-shrink: 0` gave a grid item real min-content width to push back against. Same bug class as the dev-momentum label fix from Phase 5, just triggered by new content this time.

**Added a 1D window option and made Market Snapshot window-aware too, plus exact-date tooltips everywhere (2026-07-24).** User wanted "vs. yesterday" available as an explicit window choice (not just the implicit default), and wanted Market Snapshot — the one panel that never got a selector in the original window-feature pass — to participate too. Adding `{ label: "1D", days: 1 }` to the single shared `WINDOW_OPTIONS` array threaded it through every panel for free. Market Snapshot needed real redesign, not just a selector bolted on: Open/High/Low were previously always "today's" values, which has no obvious window-aware meaning, so redefined them as *period* stats over the selected window — Open = the opening price on the first day of the window, High/Low = the highest/lowest the index touched at any point across it — while Close stays pinned to the latest price regardless of window (a "close" from mid-window wouldn't mean anything). This is the same "the window selector forces a real redefinition, not just a UI change" pattern as the original Sector Rotation/Macro rework. Separately, user asked that every comparison chart show the *exact dates* being compared on hover, not just rely on the viewer to infer them from the selected window length — important because `compoundReturn`'s window boundary and the actual comparison boundary aren't the same date: a daily-return series values day T against day T-1's close, so the true start of an N-day comparison is one trading day *before* the first row inside the window, not the first row itself. Got this wrong in an early pass (used the first in-window row's own date) before catching it via the date-range math, not a screenshot. Both `compoundReturn` and `windowDeltaByGroup` now return `{ value, startDate, endDate }` instead of a bare number, and `divergingBarChart` gained a `dateRanges` param that renders as a Chart.js tooltip `afterLabel` line; Market Snapshot's KPI tiles get the same information via a native `title` attribute since they're not canvas elements. Verified the exact tooltip content (not just that *a* tooltip appears) by driving `chart.tooltip.setActiveElements()` programmatically in a headless page and reading `tooltip.body[].after` — confirms the specific string shown, not just presence. Also re-confirmed the mobile `.window-selector` still doesn't overflow with a 5th button (was genuinely worried, given this exact area's bug history) — `docScrollWidth` stayed under `innerWidth` with real headroom to spare; the visually "cut off" rightmost buttons in a raw screenshot were the same known Edge-headless scrollbar-gutter artifact caught once already, confirmed again via DOM measurement rather than trusting the screenshot.

**Backfilled 365 days of history (2025-07-22 through 2026-07-21) directly into silver, bypassing bronze/R2 entirely (2026-07-26).** User wanted every chart populated immediately instead of waiting weeks for real accumulation, explicitly scoped to market/macro/attention/research pace — GitHub stars were left out on purpose, since GitHub's API has no historical star-count endpoint (only current `stargazers_count`), so a real backfill there would mean paginating the full stargazer list, rate-limit-prohibitive for repos with 100K+ stars. Bronze is a daily-*overwritten* staging table (see "Bronze is overwritten each run" above) — not a place to land a bulk historical file — so the backfill script talked to `workspace.silver.*` directly over the SQL warehouse connector: build each source's historical rows locally (yfinance bulk history, FRED's `observation_start`/`observation_end` range, Wikipedia's existing date-range URL pattern extended from 10 days to 365, and 365 paced arXiv trailing-7-day queries for research pace since arXiv has no way to get a day-by-day breakdown in one call), load into a throwaway staging table, then `MERGE INTO` the real table keyed by the same natural keys `bronze_to_silver.py` already uses, then drop staging. Zero changes to any daily-pipeline file — silver's MERGE-by-key design and gold's full-recompute-every-run design meant the backfill just needed to land history once, then the *unmodified* daily pipeline recomputed gold and republished on its own. Took three attempts to get the arXiv leg right: attempt 1 hit a 429 with no backoff at all; attempt 2 added 429-specific backoff but didn't catch a plain connection timeout (different exception path entirely, never even reached the status-code check); attempt 3 wrapped the whole request in a try/except covering both cases with exponential backoff, and completed cleanly in 53 minutes. Also hit a real, pre-existing bug this surfaced rather than caused: `pull_market_data.py`'s `dropna(how="all")` let through a row with real volume but NaN OHLC (yfinance returning a not-yet-settled trading day), and Python's `json.dumps()` silently serializes `float('nan')` as a bare `NaN` token — valid to Python, invalid per the JSON spec, and rejected outright by the browser's `JSON.parse()`, breaking every chart fed by that file while unrelated panels (macro, attention, dev, research) kept working fine. Fixed at the root (`dropna(subset=[...])` requiring the actual OHLC columns) and added a defense-in-depth sanitizer in `export_gold_to_json.py` that turns any NaN/inf float into `null` before dumping, with `allow_nan=False` as a hard backstop so any *future* gap fails loudly in CI instead of silently shipping broken JSON. Verified the actual fix, not just "no error thrown," by cross-checking silver row counts against gold row counts against the live exported JSON at every step (a genuine false alarm along the way — a stale Fastly CDN edge showing the old file for a few minutes looked identical to a real export bug until re-checked with a cache-busting query param) — and confirmed in the browser itself: Sector Rotation's "All" window now shows real compounded annual sector returns, Volatility shows an actual rolling-20-day trend line across the full year instead of a "collecting" meter, and the Macro rates chart shows real month-over-month deltas instead of permanently-pending KPI tiles.

**Added two trading-volume-share donut charts (sector, AI basket) purely because the user likes the visual, with a real rigor tradeoff made explicit and chosen deliberately (2026-07-26).** Before writing any code, loaded the project's own dataviz skill for chart-color guidance and found something that changed the plan: it treats donut/pie charts the same as scatter plots and choropleths (any two slices get compared side by side, not just neighbors), and under that rule its validated palette only guarantees colorblind-safe separation for 3 real categories before a fold to "Other" is required — the skill's actual recommended form for part-to-whole data is a horizontal bar, not a donut, for exactly this reason. Surfaced this to the user with three concrete options (strict 3-slice donut, a richer donut with relaxed rigor, or the recommended horizontal bar instead) rather than silently picking one; user chose the richer donut, explicitly accepting reduced CVD rigor for a fuller look. Extended the existing 5-hue categorical palette to 7 (muted green, muted violet) rather than invent something new, running the actual validator (`validate_palette.js`, light and dark) instead of eyeballing — landed in the legal 6–8 CVD WARN band, which is only legal when shipped with secondary encoding, so every slice gets a legend entry, a hover tooltip, and (implicitly) never relies on color alone. The two donuts needed genuinely different color-assignment strategies: the sector donut folds 11 sectors to top-6-by-volume + "Other," and since *which* 6 sectors make the cut changes daily, colors are assigned by rank position each render (a deliberate, documented simplification — "color follows the entity, never its rank" is the stricter rule, but a daily-changing top-N ranking has no stable per-entity slot to give a fixed color to in the first place). The AI basket donut, by contrast, has a fixed 7-ticker roster that never changes day to day, so it gets genuinely fixed per-symbol colors — the more correct pattern, used where the data actually allows it. Both needed new gold-layer work: `sector_rotation` gained a `volume` column, and a new `ai_basket_detail` table was added (per-symbol AI basket rows; the existing `ai_vs_market` table only ever had the basket-level average, never individual holdings). Verified with fabricated multi-symbol test data locally before touching the real pipeline (same empirical-first pattern as every other new chart type this project has shipped), then confirmed against real backfilled data after running the actual pipeline — one unrelated transient failure along the way (a Wikipedia pageviews 404, same class of flaky-external-API issue as the yfinance lock error from the backfill work, fixed by retrying).

**Added `analysis/key_findings.ipynb`, a separate monthly-refreshable notebook, after the user asked what would make this project stand out more as an entry-level data-analyst portfolio piece (2026-07-26).** The honest gap identified: everything up to this point is pipeline and presentation engineering, genuinely strong for that, but there was no place where the accumulated data got actually *analyzed* for a finding, which is what a data-analyst (as opposed to data-engineer) role is more likely to probe for. Rather than proposing findings from first principles, actually queried the live exported JSON for five candidates and reported real numbers back: AI basket +29.5% vs. S&P +17.4% cumulative return; a public-attention spike preceding an AI-outperformance swing; NVDA at 49% of AI-basket trading volume; sector returns splitting cleanly by rate sensitivity with Energy the one exception; and a volatility spike to ~2x baseline in early April. Asked to look deeper at the attention-leads-stock question specifically, ran it two genuinely different ways rather than confirming the first anecdote: a full-year day-to-day lag-correlation scan (21 lags tested, all weak and scattered, no reliable relationship) and a separate event study on just the five biggest attention spikes (a real but small-sample gap, honestly labeled as suggestive rather than proven). That the rigorous test *complicated* the anecdotal one, rather than confirming it, was reported as-is rather than smoothed over. The notebook itself pulls straight from the live dashboard's published JSON (same files the dashboard reads) rather than any local snapshot, so re-running it any month picks up everything accumulated since with no setup beyond `pip install -r analysis/requirements.txt`. Built by generating the `.ipynb` JSON programmatically (a throwaway Python script, not committed) rather than hand-writing notebook JSON, then actually executed via `jupyter nbconvert --to notebook --execute --inplace` so the committed file has real baked-in numbers, tables, and matplotlib charts that render on GitHub without anyone needing to run it first — confirmed zero execution errors and spot-checked several rendered charts before committing, rather than trusting "it ran" alone.

**The notebook's narrative cells went through three real rounds before landing, driven by explicit user correction each time, not by pre-planning (2026-07-26).** Round 1 added a static markdown "Business takeaway" cell under each analysis section, explaining what the chart/output meant. Rejected: "these takeaway text cells seem to simply explain how to interpret the visuals, rather than provide a concrete takeaway. I want a key finding tied to concrete analysis based on our output." Round 2 converted these to dynamic *code* cells (`display(Markdown(f"..."))`) that reference the actual computed variables from the section above (`spread`, `top_symbol`, `exceptions`, `vol_max`, etc.) and state a specific number or entity — e.g. "NVDA accounts for 49% of the AI basket's combined trading volume, nearly as much as the rest of the basket combined." Being code cells rather than static text means the finding text is regenerated from real data on every re-run, not just left stale after the underlying numbers move next month — the same "make it easy to update monthly" requirement that shaped the rest of the notebook. Round 3, after "now we need to turn the findings into insights/takeaways," added a further "Insight" code cell after each "Key finding" cell, interpreting it for a specific decision-maker persona (investor, risk manager, someone marketing the basket) with an actionable so-what — e.g. "anyone marketing or evaluating this basket as diversified AI exposure should treat that claim skeptically, since NVDA alone is doing most of the work." The general lesson, consistent with bug #11 elsewhere in this file (a technically-correct chart that communicated nothing): a technically-correct explanation of *how to read the output* is not the same thing as *what the output means*, and neither of those is the same as *what someone should do about it* — three genuinely different things worth checking are actually present, not assuming the first one covers the other two.

**A schema-patch script silently corrupted two em dashes into mojibake while fixing an unrelated `NotebookEdit` limitation, caught by an explicit `content.count()` check rather than a visual scan (2026-07-26).** Converting a markdown cell to `code` via `NotebookEdit` doesn't auto-populate the schema-required `outputs`/`execution_count` fields a real code cell needs, so `jupyter nbconvert --execute` failed validation until a one-off Python patch script added them. That script opened the notebook file with plain `open()`/`open(path, "w")` — no explicit `encoding="utf-8"` — and Windows' non-UTF-8 default silently mangled the file's two real em-dash characters (inside matplotlib chart-title strings) into `â€”` on the round trip. Caught by grepping the post-patch content for the mojibake byte sequence rather than trusting that "the script ran without error" meant the content was untouched; fixed with an explicit UTF-8 read/replace/write, then the affected chart titles were reworded (dash to colon/comma) while at it, and the notebook was re-executed to confirm no error and no remaining mojibake anywhere. General lesson: any read-modify-write round trip on a text file on Windows needs an explicit `encoding="utf-8"` on both the read and the write, since the platform default isn't UTF-8 and a corruption like this produces no error at all, just silently wrong bytes.

## Bugs found and fixed (the non-obvious ones)

Roughly chronological. Several of these were only caught by actually running things (locally, in CI, or via headless-browser screenshots) rather than by code review — that pattern held up repeatedly and is worth continuing.

1. **`read_files(...)` schema inference failure on the first bronze table.** Our JSON is pretty-printed (multi-line), but Spark's JSON reader defaults to line-delimited. Fix: `multiLine => true`.
2. **`DELTA_METADATA_MISMATCH` on bronze overwrite.** After `pull_market_data.py`'s output shape changed (single object → `{records: [...], fetched_at}`), overwriting the old bronze table's schema needs `.option("overwriteSchema", "true")` — `mode("overwrite")` alone doesn't replace schema.
3. **Serverless Databricks Job tasks need an explicit `environments` block.** `InvalidParameterValue: An environment is required for serverless task`. Fixed by adding `environment_version: "3"` and wiring `environment_key` on each task.
4. **A `melt_named_structs` abstraction in `bronze_to_silver.py` had a duplicate-column bug** (struct's own `.date` field collided with an externally-computed `date` column via `.* ` expansion). Simplified to explicit per-source blocks instead of one clever shared helper — matches the general steer toward avoiding premature abstraction.
5. **`.gitignore` almost silently broke publishing.** An unanchored `data/` pattern (meant to ignore local scratch dirs like `ingestion/data/`) was also matching `docs/data/` — the actual published output. Caught because the "Commit and push updated data" step failed with "paths are ignored." Fixed with anchored `/data/` and `/ingestion/data/`.
6. **arXiv API 500s on `max_results=0`.** Wanted just the `totalResults` count without fetching entries; `max_results=1` works, `0` doesn't.
7. **Literal `+` characters in a manually-built query string got double-encoded by `requests`** (`+` → `%2B` instead of being read as a space), silently zeroing out arXiv result counts (200 instead of 785). Fixed by using real spaces and letting `requests` percent-encode them correctly.
8. **Chart.js bars rendering at ~1/4 height, only under `responsive: true` + `maintainAspectRatio: false`.** An initial-sizing race — the canvas gets measured before its container's layout (inside a newly-inserted grid/flex parent) has actually settled. Fixed with a `requestAnimationFrame`-deferred `chart.resize()` after every chart creation (`deferredResize()` helper). Confirmed via headless-Edge screenshots with a minimal isolated Chart.js test page before touching the real dashboard code.
9. **Rotated x-axis labels clipping within their own canvas** at narrow (mobile) widths — the *last* category's rotated label has no neighbor to share space with. Fixed with a consistent 45° rotation (not an auto 0–40° range), more right-side chart padding, and shortening `dev_momentum` labels to bare repo name (full `owner/repo` still in the tooltip).
10. **The Market Snapshot range-bar chart's x-axis auto-started at 0**, so a ~40-point daily high/low spread on a ~7500 base rendered as an invisible sliver. Fixed by explicitly scaling the axis to the actual low/high range with padding.
11. **`attention_index` was showing 100 for every article and looked broken — it wasn't broken, it was badly designed.** The metric is `views / baseline_views * 100` where baseline = each article's first-observed day; with only one day of history, baseline always equals today, so it's trivially 100 for everyone. On top of that, a *bar chart* of a trend-indexed metric was the wrong chart type from the start — it can never show "rising or falling" even with more data. Fixed by conditionally showing raw pageviews (informative immediately) until 2+ distinct days exist, then switching to a multi-line chart of the indexed trend over time. General lesson: a metric/chart can be technically correct and still be uninformative by construction — worth sanity-checking what a visualization *actually communicates* on day one, not just whether the numbers are right.
12. **The S&P 500 card's % change was identical across every window (2026-07-25), caught by the user actually using the dashboard, not by review.** Root cause: `filterByWindow`'s cutoff (`latest - days`, inclusive) spans `days + 1` calendar days — correct for `windowDeltaByGroup`, which needs two distinct endpoint rows N days apart, but wrong for `compoundReturn`, which chains *already-relative* `daily_return` values. Each `daily_return` row already encodes a 1-day-back comparison, so an "N-day window" only needs to span exactly N days, not N+1 — the extra day silently compounded one return too many. Concretely, this made "1D" compound *both* yesterday's and today's return instead of just today's, and with only 2 real return-rows in history so far, every window ≥1D ended up including the same 2 rows, hence identical numbers everywhere. Fixed with a `periodSpanDays()` adjustment (`days - 1`, floored at 0) applied only where daily-return chaining or period-range aggregation is happening — `compoundReturn` internally, and Market Snapshot's separate Open/High/Low windowing (which had the identical bug, showing yesterday's open blended into "today's" range). `windowDeltaByGroup` and the raw trend-line window filters were confirmed already correct and left untouched — this was a narrow, mechanism-specific bug, not a `filterByWindow` API problem.
13. **`volatility` gold table reported a value from just 2 real returns, labeled as a "rolling 20-day" figure.** `STDDEV(...) OVER (ROWS BETWEEN 19 PRECEDING AND CURRENT ROW)` doesn't require the frame to actually be full — it happily computes sample stdev from however many rows exist, so it started emitting numbers the moment 2 daily returns existed instead of waiting for 20. Since the dashboard's gating logic only checks `rolling_20d_volatility !== null`, this bypassed the "N/20 trading days collected" progress meter entirely and showed a statistically meaningless value as if it were a real 20-day figure. Fixed by adding a running count of real (non-null) returns and gating the `STDDEV` behind `return_count >= 20` in SQL, so it stays `NULL` — and the dashboard correctly shows the accumulation meter — until a true 20-observation window exists. Found via audit, not user report; same class of bug as #12 (a window computation that doesn't actually enforce its stated size).
14. **Cleaned up three dead gold columns** (`sector_rotation.trailing_5d_return`, `dev_momentum.weekly_star_growth`, `research_pace.change_from_prior_week`) found during the same audit. All three were the *original*, fixed-window implementation of "return/growth over time," superseded when the per-chart window-selector feature added equivalent (and more flexible) client-side computation — confirmed via grep that `dashboard.js` no longer references any of them before removing.
15. **`pull_market_data.py` could write a row with real volume but NaN OHLC, which then broke the entire dashboard, not just Market Snapshot.** Surfaced during the 2026-07-26 historical backfill when yfinance returned a not-yet-settled trading day; `history.dropna(how="all")` only drops a row if *every* column is NaN, so a volume-present/OHLC-NaN row sailed through as "latest." Python's `json.dumps()` then serialized that NaN as a bare, unquoted `NaN` token — legal to Python (`allow_nan=True` is the default) but not valid JSON, so the browser's `JSON.parse()` threw and every chart reading `market_daily.json` (Market Snapshot, Sector Rotation, Volatility, AI-vs-market) broke at once, while unrelated panels sourced from other tables kept working — a useful diagnostic signal in hindsight. Fixed at both ends: `dropna(subset=["Open","High","Low","Close"])` so ingestion never selects a partially-null row as "latest," and `export_gold_to_json.py` now sanitizes any stray NaN/inf to `null` before dumping (with `allow_nan=False` as a hard backstop, so a *future* gap fails loudly in CI instead of silently shipping broken JSON to the live site).
16. **The scheduled pipeline actually failed for the first time in production on 2026-07-27**, a real arXiv 429 with zero retry logic in `pull_research_pace.py`. This was a known-fixable failure mode; the same retry-with-backoff pattern already existed in the (now-deleted) one-off historical backfill script, since its arXiv leg hit the identical error during the 2026-07-26 backfill, but that fix was never ported back into the recurring daily script that hits the same API every single run. Fixed by adding the same backoff loop (handles both 429s and generic request exceptions) to `pull_research_pace.py`, then manually re-ran the pipeline for the day and confirmed the auto-opened GitHub Issue closed itself on the next success, per the existing failure-alerting design. Lesson worth remembering: a resilience fix built for a one-off script doesn't automatically protect the recurring script hitting the same external dependency, they need to be checked separately.
17. **A `NotebookEdit`-driven schema patch silently corrupted em dashes into mojibake via a Windows default-encoding round trip (2026-07-26).** `open()`/`open(path, "w")` without an explicit `encoding="utf-8"` doesn't error on Windows, it just isn't UTF-8 — a plain read-modify-write of `key_findings.ipynb` to patch in missing `outputs`/`execution_count` fields (see the matching design-decision entry above) mangled two real em-dash characters into `â€”` with zero errors or warnings anywhere. Caught only by explicitly grepping the post-patch content for the mojibake sequence, not by re-reading it visually. Fixed with an explicit UTF-8 read/write. Full detail in the design-decision entry above.
18. **The scheduled pipeline failed a second time in production on 2026-07-31, this time in `pull_attention_data.py`**, which had zero retry logic despite `pull_research_pace.py` already having been hardened after an analogous arXiv failure on 2026-07-27 (bug #16) — the exact "a fix for one script doesn't protect a different script hitting a similar problem" lesson recurring with a different API. Root cause was more specific than a generic transient error though: Wikimedia's pageviews API 404s the *entire* requested date range when the range's end date (today) hasn't been published yet, rather than returning the range minus the unready trailing day(s) — confirmed by re-hitting the exact failing URL a couple hours later and getting a clean 200. A bare retry-with-backoff wouldn't have fixed this, since the gap is a publish lag measured in hours, not a network blip retries can ride out within a single CI run. Fixed by walking the end date back a day at a time on a 404 (up to 4 days, matching the "couple of days" lag the script's own docstring already documented), keeping retry-with-backoff for genuine transient errors at each end date first. Manually re-ran the pipeline after the fix, confirmed success, and confirmed the auto-opened GitHub Issue closed itself on the next success, same as bug #16.
19. **`pull_market_data.py` silently skipped a whole trading day (2026-08-03) rather than failing loudly, caught by the user noticing the dashboard "stuck" on 2026-07-31 data (2026-08-04).** No workflow run actually failed this time — every run reported success, which is what made this one harder to catch than bugs #16/#18. Root cause: the script only ever captured the single most-recent *settled* day per run (`history.iloc[-1]`), and Yahoo/yfinance's backend hadn't finalized Monday 2026-08-03's close by the time Tuesday's scheduled run fired (~08:15 UTC) — confirmed by re-running the identical query a few hours later and getting 2026-08-03 (and a fresher 2026-08-04) cleanly. Because only one day gets captured per run, once the pipeline moved on to whatever was "latest" on the next run, 2026-08-03 was gone for good with no self-correction mechanism — a fundamentally different failure shape than bugs #16/#18 (those were retryable transient errors; this was silent data loss with a green checkmark). Fixed at the design level rather than papering over the specific date: `pull_market_data.py` now captures the trailing 3 settled days per symbol every run instead of just 1, verified safe by checking `bronze_to_silver.py` first — it already `explode()`s the `records` array and `MERGE`s by `(symbol, date)`, so it never assumed one row per symbol per run, meaning the fix needed zero downstream changes and turned every daily run into a mini self-healing backfill of its own trailing window. Almost built a one-off manual backfill script for the missing date (following the now-familiar pattern) before realizing the real fix would recapture 2026-08-03 automatically on its own since it was still inside the trailing 3-day window — deleted the throwaway script unused rather than run both. One genuine false alarm along the way, also previously documented from the 2026-07-26 backfill work: right after the fix landed, a plain `curl` of the live JSON still showed the gap, which for a moment looked like the fix hadn't worked — a cache-busting query param immediately showed the correct, complete data, confirming it was a stale Fastly CDN edge, not a real problem. Lesson worth repeating: verify freshness claims about a GitHub Pages-hosted JSON file with a cache-busting param before concluding a fix didn't work.
20. **A user running `monitoring/daily_report.ipynb` locally ("Run All") hit a bare `KeyError: 'DATABRICKS_HOST'`, and investigating it uncovered a much bigger, real production incident happening at the exact same time (2026-08-07).** The local error itself was straightforward and by design: this notebook queries Databricks directly and has no zero-credential mode like `analysis/key_findings.ipynb`, and `databricks/warehouse.py`'s `os.environ["DATABRICKS_HOST"]` raises a raw `KeyError` with no explanation if the variable isn't set, which it never is locally. Fixed with an explicit pre-check in the notebook's own setup cell (not in `warehouse.py`, which other scripts already use correctly and always have these set) that names the missing variable and points to `monitoring/README.md`. The very next verification run caught a *second*, completely independent failure this exact fix was needed for: `pull_market_data.py` raised on a single bad symbol (XLV, no usable yfinance data that run) and discarded all ~30 other symbols' perfectly good data with it — same failure shape one layer deeper, fixed the identical way (skip the one bad symbol, only raise if literally all of them fail). Both fixes lean on `bronze_to_silver.py`'s `MERGE`-by-natural-key design already being safe to receive partial data, the same property bug #19's fix relied on. `monitoring/daily_report.ipynb`, built the day before this incident, is what makes the isolation fix trustworthy rather than a silent-degradation risk: it flagged the exact set of stale tables correctly during the live incident (`CHECK DATA` verdict, naming `market_daily`/`sector_rotation`/`ai_vs_market`/`ai_basket_detail`/`volatility` as stale) before either fix landed, real proof the report does what it was built for on the very first real incident after being wired in.

## Things to remember about how this user likes to work

- Wants to see real output, not just be told something works — screenshots (via headless browser), live-URL checks with a fresh/incognito session, actual query results, not just "the workflow succeeded."
