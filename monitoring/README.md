# Pipeline Run Report

An operational health check, regenerated by the pipeline itself on every run and overwritten in place - not a historical log. `analysis/key_findings.ipynb` asks what the accumulated data means for AI investing; this notebook asks a narrower, more mechanical question: did the latest run actually work, and does the data it produced look right?

(The pipeline runs weekly now; the file is still named `pipeline_report` after its earlier daily-report role, kept stable so links and history don't break.)

**[`pipeline_report.ipynb`](pipeline_report.ipynb)** checks three things every run:

1. **Did the pipeline run?** Pulled from the GitHub Actions API directly, plus a check for any open `pipeline-failure` issue - independent of what the data itself looks like, since a run can report success while still landing incomplete data (this happened for real on 2026-08-03). On a recovery run it also reads this run's own transform/export step outcomes, since a report running inside the pipeline can't see its own run's final conclusion.
2. **Does the data look right for the run?** Queries every gold table directly in Databricks (not the published JSON, which is only a downstream copy) and checks each source's freshness against its own cadence - trading-day sources are expected to go quiet on weekends, CPI/unemployment/fed funds are expected to sit still for weeks between monthly releases, and Wikipedia's attention data is expected to run 1-2 days behind. Each check runs at generation time, when a healthy run has just landed fresh data, so it validates "did this run land data" rather than "is the weekly cadence being met." None of the quiet cases is a problem; the report is built to know the difference between "quiet as expected" and "actually stale."
3. **Where does everything live?** A reference table mapping every gold table back to its silver and bronze sources and the dashboard panel it feeds, so a real problem can be traced end to end without re-deriving it from `PROJECT_PLAN.md` each time.

## How to read it

**Don't run it - open it.** The pipeline already executes this notebook on each run and commits the result with real output baked in, so opening the file shows the latest report without running anything yourself:

- Simplest: view [`pipeline_report.ipynb`](pipeline_report.ipynb) directly on GitHub. It renders the saved output natively, no pull, no IDE.
- Or `git pull` and open the file locally - as long as you don't hit "Run All," you're just looking at the same already-executed output.

Clicking "Run All" re-executes every cell live against Databricks, which needs real credentials this notebook has no local-friendly way to get (see below) - and isn't necessary, since the committed version already has the latest run's real numbers in it.

### If `git pull` won't update it

The pipeline rewrites and commits this file every run, so it must be clean in your working tree for a pull to fast-forward. Opening it in an IDE can quietly dirty it - VS Code, for instance, stamps its own kernel name and Python version into `metadata.kernelspec` / `metadata.language_info` the moment it attaches a kernel, even if you change nothing and never hit save-as. Git then refuses to overwrite that edit on pull.

The change is always cosmetic (two metadata lines, never the code or the report), so just throw it away and pull:

```
git restore monitoring/pipeline_report.ipynb
git pull
```

Cleanest habit: read the report on GitHub (it renders the saved output with no pull and no IDE). Only open the file locally when you actually need to, and let the editor treat it as read-only.

## Why this one needs credentials and the other doesn't

`analysis/key_findings.ipynb` reads the published JSON on GitHub Pages, which needs nothing but `requests`. This notebook queries Databricks directly, so it can catch a case where the export/publish step itself is the thing that's broken. That means *executing* it requires `DATABRICKS_HOST`/`DATABRICKS_TOKEN` - the same credentials the rest of the pipeline uses, set as GitHub Actions secrets that only exist inside CI. It isn't meant to be run casually the way the analysis notebook is; it's meant to run unattended, inside the pipeline's own CI job. Hitting "Run All" locally without them raises a clear error explaining exactly this, rather than a bare `KeyError` from deep inside `databricks/warehouse.py`.

## How it runs

The `pipeline.yml` workflow executes and commits this notebook as its last step, after ingestion, transform, and export - and it runs even if an earlier step failed, specifically so a bad run still produces a report explaining what went wrong rather than silently skipping it. Every run's version replaces the last; there's no separate archive. If you want the trail of what happened on a specific past run, `git log --follow -- monitoring/pipeline_report.ipynb` has every version that was ever committed (`--follow` because the file was `daily_report.ipynb` before 2026-09-01).
