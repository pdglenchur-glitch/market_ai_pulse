# Daily Pipeline Report

An operational health check, regenerated by the pipeline itself every day and overwritten in place - not a historical log. `analysis/key_findings.ipynb` asks what the accumulated data means for AI investing; this notebook asks a narrower, more mechanical question: did today's run actually work, and does the data it produced look right?

**[`daily_report.ipynb`](daily_report.ipynb)** checks three things every day:

1. **Did the pipeline run?** Pulled from the GitHub Actions API directly, plus a check for any open `pipeline-failure` issue - independent of what the data itself looks like, since a run can report success while still landing incomplete data (this happened for real on 2026-08-03, see `PROJECT_MEMORY.md` bug #19).
2. **Does the data look right for the day?** Queries every gold table directly in Databricks (not the published JSON, which is only a downstream copy) and checks each source's freshness against its own cadence - trading-day sources are expected to go quiet on weekends, CPI/unemployment/fed funds are expected to sit still for weeks between monthly releases, and Wikipedia's attention data is expected to run 1-2 days behind. None of that is a problem; the report is built to know the difference between "quiet as expected" and "actually stale."
3. **Where does everything live?** A reference table mapping every gold table back to its silver and bronze sources and the dashboard panel it feeds, so a real problem can be traced end to end without re-deriving it from `PROJECT_PLAN.md` each time.

## Why this one needs credentials and the other doesn't

`analysis/key_findings.ipynb` reads the published JSON on GitHub Pages, which needs nothing but `requests`. This notebook queries Databricks directly, so it can catch a case where the export/publish step itself is the thing that's broken. That means running it requires `DATABRICKS_HOST`/`DATABRICKS_TOKEN` - the same credentials the rest of the pipeline uses, set as GitHub Actions secrets. It isn't meant to be run casually the way the analysis notebook is; it's meant to run unattended, inside the pipeline's own CI job, where those credentials already exist.

## How it runs

The `pipeline.yml` workflow executes and commits this notebook as its last step, after ingestion, transform, and export - and it runs even if an earlier step failed, specifically so a bad day still produces a report explaining what went wrong rather than silently skipping it. Every day's version replaces the last; there's no separate archive. If you want the trail of what happened on a specific past day, `git log -- monitoring/daily_report.ipynb` has every version that was ever committed.
